# Atomberg MES — Order to Output

A full-stack Manufacturing Execution System built for the Atomberg Software Engineer take-home assignment. Covers 14 days of factory data across four machines, three user personas, a REST API, and a React frontend.

---

## Running locally

### Prerequisites

- Python 3.10+
- Node.js 18+

### 1. Clone and set up the backend

```bash
cd atomberg/backend
pip install -r requirements.txt
python seed.py --reset          # loads all CSVs into mes.db
python -m uvicorn main:app --reload --port 8000
```

API is now live at `http://localhost:8000`.  
Interactive docs: `http://localhost:8000/docs`

### 2. Set up and run the frontend

```bash
cd atomberg/frontend
npm install
npm run dev                     # starts Vite dev server at http://localhost:5173
```

The Vite dev server proxies all `/api/*` requests to `http://localhost:8000`, so no CORS configuration is needed during development.

### 3. Production build

```bash
cd atomberg/frontend
npm run build                   # outputs to frontend/dist/
```

Serve `dist/` with any static host and point the API origin via the `VITE_API_BASE` env var, or deploy the FastAPI app with `uvicorn main:app` and serve the built `dist/` from the same origin.

## Schema and indexes

Six tables mirror the six CSV files. FK constraints and `PRAGMA foreign_keys = ON` are enforced at the connection level.

```sql
machines          (machine_code PK, name, target_units_per_hour)
skus              (sku_code PK, description, std_cycle_time_sec)
downtime_reasons  (reason_code PK, description, category CHECK planned|unplanned)

orders (
  order_no PK,
  sku_code        → skus,
  machine_code    → machines  (nullable — unassigned orders allowed),
  qty_planned, due_date, priority CHECK low|normal|high,
  status CHECK planned|released|in_progress|on_hold|completed|cancelled,
  created_at, updated_at
)

unit_events (
  event_id PK,
  machine_code    → machines,
  order_no        → orders,
  completed_at, serial_no
)

downtime_events (
  downtime_id PK,
  machine_code    → machines,
  started_at, ended_at (NULL = still running),
  reason_code     → downtime_reasons,
  note
)
```

### Index reasoning

| Index | Rationale |
|---|---|
| `orders(status)` | Planning desk filters by status constantly |
| `orders(machine_code)` | Floor snapshot + per-machine analytics |
| `orders(due_date)` | Date-range queries and "due this week" |
| `orders(priority)` | Priority filter in planning desk |
| `unit_events(machine_code)` | Per-machine output counts |
| `unit_events(order_no)` | Progress % per order (COUNT join) |
| `unit_events(completed_at)` | Time-bounded analytics — the hot column on an 80k-row table |
| `downtime_events(machine_code)` | Per-machine downtime sums |
| `downtime_events(started_at)` | Period-range downtime queries |
| `downtime_events(reason_code)` | Top-reasons rollup |

The schema is written by hand in `schema.sql` with explicit `CREATE TABLE` statements rather than generated by an ORM, as required.

## API shape and reasoning

Base URL: `http://localhost:8000`  
All responses are JSON. Interactive docs at `/docs`.

### Design decisions

**Pagination everywhere** — `unit_events` has 80 k rows today and will grow. Every list endpoint accepts `page` / `page_size` and returns `{total, page, page_size, items}`. The orders list also accepts server-side filters (`status`, `machine_code`, `priority`, `search`, `due_before`, `due_after`) so the planning desk never fetches more than it displays.

**Server-side validation** — all writes go through Pydantic models with field-level constraints (regex patterns, `gt=0`, date format). FK violations are checked explicitly before the INSERT and return `422 Unprocessable Entity` with a human-readable `detail` string. The API is safe to call directly, not just through the UI.

**Simulated time** — the dataset is a snapshot frozen at `2026-08-17 09:15`. `SIMULATED_NOW` is a module-level constant used by the floor snapshot and any "is this downtime currently active?" logic. It is returned by `/health` so clients can confirm they are reading the right snapshot.

### Endpoints

| Method | Path | Purpose |
|---|---|---|
| GET | `/health` | Liveness check + simulated time |
| GET | `/machines` | All four machines |
| GET | `/machines/{code}` | Single machine |
| GET | `/skus` | All SKUs |
| GET | `/downtime-reasons` | All reason codes |
| GET | `/orders` | Paginated + filtered order list |
| GET | `/orders/{no}` | Single order with completion count |
| POST | `/orders` | Create order (full validation) |
| PATCH | `/orders/{no}` | Partial update |
| DELETE | `/orders/{no}` | Remove order |
| GET | `/unit-events` | Paginated unit completions |
| GET | `/downtime-events` | Paginated downtime events |
| GET | `/floor/snapshot` | Live machine state — one record per machine |
| GET | `/analytics/summary` | Period performance, downtime breakdown, daily output |
| GET | `/analytics/oee` | OEE (Availability × Performance × Quality) per machine |

## What was built for each persona

### Floor supervisor — Floor Display (`/floor`)

The wall display is designed to be read in one or two seconds from several metres away, with no interaction at all.

- Four large machine cards, one per machine, in a 2×2 grid.
- Each card shows: machine ID, running / stopped / idle state, the current order (SKU name, progress bar, unit count), units completed today, availability %, and downtime minutes.
- When a machine is stopped, a prominent red banner shows the reason and how long it has been down.
- Auto-refreshes every 30 seconds via `setInterval`. A countdown shows when the next refresh is. No user action is ever needed.
- Colour coding: green = running well, yellow = availability < 85 %, red = availability < 70 % or machine stopped.

### Planning team — Planning Desk (`/planning`)

The desk view is built for detail and control. The team can search, filter, create, update and delete orders without leaving the page.

- Filterable, paginated table (25 rows per page by default). Filters: free-text search on order number or SKU, status, priority, machine.
- Click any row to open a detail drawer with full order info including current progress.
- From the detail view, open an edit modal pre-populated with the current values. All fields are validated before the request is sent; server errors (e.g. duplicate order number, unknown SKU) surface inline in the form.
- Create new orders with the "+ New Order" button. The form uses the `/skus` and `/machines` lists from the API so dropdowns are always in sync.
- Delete with a two-step confirmation to prevent accidents.
- Toast notifications confirm every successful action or surface errors clearly.

### Plant manager — Management Dashboard (`/management`)

The management view is about depth and period selection, not immediacy.

- Date range picker at the top. Defaults to the full 14-day dataset. Press Apply to reload all panels.
- KPI row: total units produced, achievement % vs target, average OEE, planned downtime, unplanned downtime.
- Output vs target table per machine with a visual achievement bar.
- Stacked bar chart of daily output by machine — shows trends across the period.
- OEE table: Availability, Performance, Quality, OEE per machine.
- Stacked bar chart: planned vs unplanned downtime minutes per machine.
- Order status doughnut chart: see at a glance how many orders are completed, in progress, planned, on hold, cancelled.
- Top downtime reasons table with occurrence count, total minutes, and share of total downtime — answers "what is costing us the most?"

## Data observations and handling

**Orders without a machine** — 12 orders (`PO-2026-4157` to `PO-2026-4168`) have an empty `machine_code`. These are unassigned planned orders. `machine_code` is nullable in the schema; the seed script normalises empty strings to `NULL`.

**Unit event serial numbers** — serials follow the pattern `{sku_code}-{seq}`. The sequence numbers start mid-range on day one, implying this is a snapshot from an ongoing system, not from the very beginning of production. No data cleaning was needed; they are stored as-is.

**Open downtime events** — none of the 307 events have a `NULL` ended_at in this snapshot. All events are closed. The schema and API handle open events (the floor snapshot query explicitly checks `ended_at > sim_now` or `IS NULL`), so the system is ready for a live feed.

**Duplicate-safe seeding** — `seed.py` uses `INSERT OR REPLACE` for reference tables and `INSERT OR IGNORE` for unit events, so it is safe to re-run with `--reset` or without.

**SQLite aggregate clamping** — SQLite does not support `MIN(col, ?)` as a scalar function inside `SUM()`. Downtime duration queries clamp event boundaries to the period using `CASE WHEN` expressions instead of `MIN()/MAX()`.

## Assumptions

- Shift is 8 hours/day for target and OEE calculations. The data shows production starting around 06:00, so "today" availability is calculated against minutes elapsed since midnight.
- Quality is assumed to be 1.0 (100 %) for OEE because there is no reject or scrap data in the dataset.
- `SIMULATED_NOW = 2026-08-17 09:15` is the fixed "current time" as specified in the assignment. This is a constant in `config.py`, imported by any module that needs it.
- Orders with `status = 'in_progress'` are the ones actively running on a machine. Only one `in_progress` order per machine is expected at a time.

## What was cut, and what comes next

**Cut for time**
- Authentication and role-based access (the three personas currently share the same nav; in production each would have a separate login).
- Deployment (Render / Railway / Fly.io config).
- Unit and integration tests.
- WebSocket push for the floor display instead of polling.
- Manual chunk splitting to bring the JS bundle below 500 kB (currently ~593 kB gzipped to 169 kB, acceptable for LAN use).

**What I'd add next**
- `POST /downtime-events` — let supervisors log stoppages from the floor.
- Order scheduling / sequencing view for the planning team.
- Shift-based availability calculation (06:00–14:00, 14:00–22:00) rather than elapsed-since-midnight.
- Time-series chart of output rate within a shift to spot speed degradation.
- Export to CSV from the management dashboard.
- Persistent filters / date range saved to `localStorage`.
